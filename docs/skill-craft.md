# Skill craft

How the skills in this repo are written, and the theory behind the choices. If you're adding or editing a skill under `plugin/skills/`, this is the house style. For the prior question — *whether* a piece of surface area (a flag, a config step, a new skill) should exist at all — see [`design-principles.md`](design-principles.md).

The short version: **these skills are deliberately lean.** Every principle below serves a set that reads as if one hand wrote it — legible, single-purpose, calibrated. Where a heavier, more defensive style genuinely helps, we reach for it *surgically*, not by default. Restraint is the point, not an accident of being unfinished.

## 1. One skill, one job

Each skill owns exactly one stage of the arc (`setup-skills → spec → prd → issues → triage`, with `diagnose`/`tdd` as companions). `spec` interviews, `prd` writes, `issues` decomposes, `triage` classifies. When editing, resist letting one skill bleed into the next — interview logic does not belong in `prd`, ticket-creation does not belong in `spec`. The boundaries are load-bearing; the workflow depends on them. See `CLAUDE.md` → "The workflow arc and skill boundaries."

## 2. The description is a trigger, not a summary

A skill's `description` is the only signal the model has for *when* to fire it, so it lists trigger phrases verbatim. But it must describe **when to use**, not **how the skill works**.

Do not summarize the workflow in the description. Testing on comparable skill sets (superpowers) found that when a description restates the process, the agent acts from the description and *skips the body* — a description that mentioned "code review between tasks" produced one review even though the skill body specified two. The description becomes a shortcut the agent takes instead of reading the skill.

- **Keep:** rich trigger phrases (they drive auto-invocation), and boundary/sequence hints that disambiguate siblings (`spec` "comes before /prd… produces alignment rather than a written artifact").
- **Cut:** the step sequence, the methodology, anything an agent could mistake for the whole skill.

## 3. Match the form to the failure

Before writing guidance, classify the failure you're preventing — the form that fixes one failure type backfires on another.

| Failure | Right form |
|---|---|
| Output has the wrong shape (bloated, restated, buried) | A positive recipe: state what the output **is**, in order (the `<issue-template>`, the agent brief structure) |
| A required element gets omitted | A structural slot in the template they fill in |
| Behavior should depend on a condition | A conditional on an observable predicate (§4) |
| Knows the rule, breaks it under pressure | Prohibition + rationalization table + red flags |

Only the last row justifies bulletproofing. **Do not bulletproof recipe skills** — indiscriminate prohibitions ("never…", "don't…") negotiate poorly under a competing incentive and bloat the set. That's why exactly one skill — `spec`, whose entire value rides on "one question at a time" — carries a rationalization table. It's special on purpose. When you add a table, it should be because you watched the rule fail, not because tables look rigorous.

## 4. Conditionals on observable predicates

Key behavior to something the agent can actually check: *"If `docs/agents/domain.md` exists, read it; if it doesn't, proceed silently."* A rule tied to an observable file/state binds; vague guidance ("consider the domain vocabulary") doesn't. Prefer a conditional with a clean predicate over an unconditional rule plus exemption clauses.

## 5. Speak in stable verbs, resolve per-repo

Consumer skills (`prd`, `issues`, `triage`) never branch on issue-tracker type. They speak in stable verbs — "publish to the issue tracker", "fetch the relevant ticket", "apply the `<role>` triage label" — resolved per-repo by the docs `setup-skills` writes (`docs/agents/*.md`). If a skill needs new tracker behavior, express it as a **new verb** and add the resolution to the seed docs; never hardcode `gh`/`glab`/`bd` in a consumer skill. See `CLAUDE.md` → "The setup-skills / consumer-skill contract."

## 6. Keep SKILL.md lean; push heavy reference to companions

The always-loaded `SKILL.md` stays small; heavy reference and reusable templates live in companion files the skill links and reads on demand (`tdd/tests.md`, `tdd/mocking.md`, `triage/AGENT-BRIEF.md`). If a section is 100+ lines of reference, it's a companion, not inline.

## 7. Mark AI-generated tracker artifacts

Every triage comment or artifact starts with `> *This was generated by AI during triage.*` (and the analogous line for issue creation) so a maintainer can scan AI activity in tracker history.

## Influences, and where we diverge

[mattpocock/skills](https://github.com/mattpocock/skills) is the parent — the `spec`/`prd`/`issues`/`triage`/`tdd`/`diagnose` arc descends from its engineering skills. [superpowers](https://github.com/obra/superpowers) is the maximalist reference: a full methodology with an eval harness, multi-harness ports, and heavily bulletproofed skills. We borrow its sharpest *lessons* — description discipline (§2), match-the-form-to-the-failure (§3) — but not its *volume*. The goal here is a small, coherent, readable set a person can hold in their head, not a comprehensive process harness. When in doubt, cut.
